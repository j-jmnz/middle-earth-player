# Claude Code

The rules for every session are in `.claude/rules/authority.md`. Read it. Any session or agent that changes code also reads `.claude/rules/code-standards.md` and follows it; one that changes a doc, `docs/phases/STATUS.md` or an agent file follows `.claude/rules/docs-standards.md` (current state only, no history logs). Every commit follows `.claude/rules/commit-standards.md` (`<type>: <summary>` with type fix, feat, refactor, style or repo; branches land on `main` squashed). Branches, versions, tags and releases follow `.claude/rules/release-standards.md`: a release is only ever cut by `.github/workflows/release.yml`, a real one only when the user asks (`docs/releasing.md`, Start a release). The README, `docs/brief.md`, and `docs/architecture.md` win over anything here.

Find docs through `docs/INDEX.md`: every file an agent reads, its size, the heading tree of the long ones with line ranges, and the sections each code area cites. Read a section, not a whole file: `pnpm doc section <file> "<heading>"` (for example `pnpm doc section brief "Core round"`). After changing a doc's headings or a doc citation in code, run `pnpm doc index`; a test fails while the index is stale or a citation names no heading.

## Data

`data/` is committed and is the only thing tests and agents read for cards, scenarios and rules text. Sources are listed in `data/sources.json`.

- `pnpm data sync [ringsdb|hallofbeorn|dragncards|rules|scans|pictures|icons]` is the only command that uses the network. It refreshes `data/raw/` and the uncommitted caches under `.cache/`: PDFs, card scans (pinned by sha256 in the ledger) and every card's picture, which `pnpm assets scans` bundles so the app needs no network (picture sources, in order, are in `scripts/data/sources/pictures.ts`; shown only, never read for text). `scans` and `pictures` read `data/cards`, so a bare `data sync` skips them: run `pnpm data build`, then `pnpm data sync scans pictures`. Adding cards (a campaign, a pack, a scenario) is not done until `pictures` has run on them: a card with no picture pin is bundled from its small scan, so its art and its scenario's scene look blurred next to the others. `scripts/data/sources/pictures.test.ts` fails on a card a built scenario deals without one; add a code to its exception list only when no picture source has the card. `rules` also packs the two booklet PDFs into `assets/booklets/`, gitignored (`pnpm assets booklets` does only that).
- `data/printed/<campaign>.json` is the printed-text ledger: the lines on each card side, read from its scan. The build uses it in place of Hall of Beorn text. An effect record names the ledger lines it implements (`lines`).
- `data/rules/index.json` is the hand-checked list of rule spans (exact `from` and `to` quotes per page column); `data/rules/columns.json` holds the per-document column boxes. `data/rules/entries.json` is built from them.
- `data/prebuilt-decks.json` names the pre-built player decks: the Learn to Play's four core decks (`ltp.starter-decks`) and every decklist an official product prints (`decklist.*` spans, read from the product PDFs that `data sync rules` pins). The build resolves each row through Hall of Beorn and writes `data/decks/prebuilt.json`; a printed misspelling is an alias with its reason, a wrong heading total a recorded misprint.
- Every script logs through `scripts/log.ts` to stderr; `--verbose` adds each request, file and stack, `--quiet` keeps warnings and errors, `LOG_LEVEL` sets either. A new script calls `runScript(tag, main)` and logs with the `Log` it is handed, not `console`.
- `pnpm data build` is offline and deterministic: raw to `data/cards`, `data/scenarios`, `data/campaigns`, `data/rules`, `src/effects/generated`, the barrel of asks files (`src/play/words/asks/index.ts`), and the game icons (`assets/icons`, `src/ui/icons`). `pnpm data build -- --verbose` lists the scenarios whose cross-checks failed.
- `pnpm data check` rebuilds into a temporary directory and fails on any difference. CI runs it.
- `pnpm data query "<sql>"` queries tables `cards`, `scenario_cards` and `rules` in memory. Rules text is `select id, title, text from rules where ...`.
- `pnpm effects draft <scenario-id | starter-deck-id | pack | code,code,...>` writes `.agent/drafts/<code>.md` (not committed) for each card with a printed ledger line no effect record owns. It clears its earlier drafts, groups batch twins, and takes codes separated by commas or spaces. The `effect-author` agent turns a bundle into records in `src/effects/authored/`.
- `pnpm effects render <scenario-id | code,code,...>` (`--out <file>`, `--all-dealt`; `--all [--out <dir>]` renders every playable scenario, and `--all --out scripts/data/effects/render/snapshots` refreshes the snapshots a test compares) prints each card's printed ledger lines with the records that name them rendered as plain English, and the lines no record names. It is a reading aid; a piece with no template prints as JSON. Run it as soon as records are written, then the `reading-judge` agent on it.
- `pnpm effects open` rewrites `src/effects/open-lines.ts`, the printed lines no record owns. A test compares it, so run it after adding or changing records. `src/campaign/playable.ts` lists the scenarios whose lines are all covered.
- `pnpm test smoke <codes>` plays a seeded game with a player card's records and reports any throw, refusal or stall (`--all` runs every card). `pnpm test encounter <scenario-id>` does the same for a scenario's encounter cards and a few dozen seeded random-intent games (`--all` runs every playable scenario).

**Sources are online.** Any resource a task needs (rules PDFs, booklets, card scans, card text) comes from an online source, fetched through `pnpm data sync` and recorded in `data/sources.json`. Query the PDF when a rule or card line is in question; do not ask for a physical card, do not rely on memory, and do not paste a PDF into the repo. (User instruction, 2026-10-24.)

## Commands

Scripts are grouped as `pnpm <group> <command> [args]` (`test`, `data`, `effects`, `scenario`, `assets`, `doc`, `release`); `pnpm <group>` alone lists its commands, except `test` and `assets`, which run everything (`scripts/cli.ts`).

- `pnpm test` runs Vitest. `pnpm vitest run <file>` runs one file. No network and no prebuilt database are needed.
- `pnpm test changed` runs the tests that import a file changed since the last commit; `pnpm test fast` runs everything but the slow files (`slowFiles` in `vitest.config.mts`). `.claude/rules/code-standards.md` (Checking a change) says when to run which.
- `pnpm lint` runs Oxlint (`.oxlintrc.json`): the import boundaries and the React and Expo rules.
- `pnpm typecheck` type-checks with tsrs (the Rust port of TypeScript 7). The `typescript` package stays for the editor and the tests that parse source.
- `pnpm test scenario <scenario-id>` (`--list` first; `--quick` skips the goldens and the reader check while authoring) runs the tests that belong to one scenario (held to a time budget on a full run), its goldens, the coverage checks, the file-size, test-cost, rule-id and words checks (`--words` runs only the words tests, the asks checks too for a scenario with an asks file), the card smoke on its player cards and the encounter smoke, plus the family and manifest tests when pool, family or manifest files changed since the merge base with origin/main (docs/development.md, Commands). Use it while authoring.
- `pnpm scenario new <scenario-id>` (`--dry-run` first) writes a scenario's skeletons (game, golden, campaign and spec tests, asks file, seed finder, Maestro flows, authored effects file) and registers it in the fixture and golden registries; it refuses a scenario that has files. The procedure around it is in `docs/agents/agent-brief.md` (Scenario procedure).
- `pnpm scenario pack <scenario-id>` writes `.agent/pack/<id>.md` (not committed): the vocabulary, the schema entries the drafts' nearest records use, the cookbook sections they need and the drafts, which the scenario author reads in place of the brief's reading list.
- `pnpm move <old> <new>` (or `pnpm move <map.json>`, `--dry-run` first) moves tracked files and folders and rewrites every relative import and every root-written path in code, docs and configs that names them; a file's `.native` variants and its test go with it. It lists what it cannot follow (paths built at run time). Move files with it, not by hand.
- `pnpm scenario fixtures` rewrites the Maestro save fixtures (`src/campaign/fixtures/`) when `fixtures.test.ts` says a fixture no longer reaches its moment. `--won` also searches for scenario 1's won game, which is open (`docs/phases/STATUS.md`). `pnpm scenario fixtures <scenario-id>` writes only that scenario's file, taking the earlier parts' won games from their committed files.
- `pnpm desktop dev` opens the Electron shell on the Metro web server; `pnpm desktop build` and `pnpm desktop pack` make the web export (`EXPO_PUBLIC_DESKTOP=1`) and an installer for this OS in `desktop/out`; `pnpm desktop smoke` launches the app on a seeded export and checks it (`docs/development.md`, On a desktop). The desktop and web work never changes a phone file or the Android bundle: `pnpm test phone-bundle` and `scripts/checks/phone-files.test.ts` check it (`docs/architecture.md`, Screens).
- `pnpm android:usb --device` runs the app on a phone plugged in by USB when the phone cannot reach Metro over the network (a VPN or isolated Wi-Fi shows a blank screen and `ConnectException` to the Mac's LAN address): it forwards port 8081 with `adb reverse` and points the app at `localhost`.
- `pnpm release plan --dry-run` prints the next release tag and its notes from the commits since the last tag (`git fetch --tags` first); it changes nothing.
- `pnpm assets catalog` writes `assets/catalog.db` and `src/catalog/version.ts` from `data/`. Do not commit `catalog.db`. Commit `version.ts` when it changes; a test checks it.

## Agents

`implementer`, `reviewer`, `ux`, `orchestrator`, `effect-author`, `reading-judge` (reads each rendered record from `pnpm effects render` against its printed line; read-only) and `scenario-author` (one scenario, run by the orchestrator as the tasks of `docs/agents/agent-brief.md`, Scenario procedure) are in `.claude/agents`. `docs/agents/agent-brief.md` is the brief for an agent that owns one mechanic family (`docs/agents/effect-authoring.md`). After `implementer` reports a green exit, run `reviewer` on the diff, and `ux` as well when `src/screens` or `src/play` changed. A plan with several sections is run by `orchestrator` (`.claude/agents/orchestrator.md` sets the models and the one review round).

## Skills

`avoid-ai-writing` (`.claude/skills/avoid-ai-writing`) audits and rewrites prose for machine-written tells. Run it in `docs` context on a doc change, a pull request title and body, or anything else a person reads (the release notes are built from commit subjects). It never touches code, data or quoted card and rules text.

## Cloud sessions

`.claude/hooks/session-start.sh` installs dependencies. A cloud session has no phone, simulator, or Maestro. Phone and tablet checks are not tracked: no notes for them in STATUS, phase files or reports (user instruction, 2026-11-06).
